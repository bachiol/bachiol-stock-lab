# 바치올 주가 실험실 — 고객용 프롬프트

국내주식 시세와 공시 재무정보를 조회하는 로컬 웹 프로그램을 만드는 7단계 프롬프트입니다. 투자 추천·자동매매 기능은 포함하지 않습니다.

먼저 `01_시작안내.txt`를 읽어 주세요. 아래 코드 블록을 0번부터 6번까지 하나씩 같은 프로젝트의 AI 코딩 도구에 입력합니다. 한 단계의 완료 결과를 확인한 뒤 다음 단계로 넘어갑니다. API 문서를 읽을 수 없거나 키가 준비되지 않은 단계는 실제 연결을 완료한 것으로 처리하지 않습니다.

## 프롬프트 0 — 공통 규칙

```text
이 폴더에 "바치올 주가 실험실"이라는 로컬 웹 프로그램을 단계별로 만들 거야. 먼저 아래 공통 규칙을 AGENTS.md 파일로 저장하고, 앞으로 모든 작업에서 지켜줘. 이번에는 AGENTS.md만 만들고 다른 코드는 작성하지 마.

[프로그램의 성격]
- 국내 상장종목 하나를 조회해, 공개적으로 알려진 워런 버핏의 투자 관점을 다섯 가지 질문으로 정리해 보여주는 기업 정보 확인 도구다.
- 투자 추천 도구가 아니다. 종합 점수, 등급, 매수·매도 의견, 목표주가, "싸다/비싸다" 같은 판정을 화면에 만들지 않는다.
- 워런 버핏이나 버크셔 해서웨이의 공식 도구·공식 기준이 아니라는 점을 화면에 밝힌다.

[기술 조건]
- 현재 지원 중인 Node.js LTS를 사용한다. 우선 내장 모듈로 구현하되, ZIP·XML 처리를 직접 구현하기 어려우면 유지보수되는 최소 의존성을 사용하고 용도와 버전 및 잠금 파일을 남긴다.
- server.mjs가 127.0.0.1의 4318 포트에서만 열리고, public 폴더의 지정한 파일만 제공한다.
- 브라우저는 우리 서버의 /api/... 만 호출한다. 외부 API는 서버에서만 호출한다.

[인증 정보]
- 폴더의 .env.local에서 KB_APP_KEY, KB_APP_SECRET, OPENDART_API_KEY를 서버가 읽는다. 값을 새로 만들거나 바꾸지 않는다.
- 키, 시크릿, 접근 토큰, IP, MAC 주소를 답변, 소스코드, 브라우저 응답, 로그, 오류 메시지, 테스트 출력에 절대 표시하지 않는다. 설정 여부는 "설정됨/설정되지 않음"으로만 말한다.
- .env.local과 캐시 폴더는 .gitignore에 넣고 웹으로 제공하지 않는다.

[데이터 원칙]
- 시세·종목 정보는 KB증권 Open API, 다년 재무·현금흐름은 금융감독원 OpenDART에서 가져온다. 화면에서 두 출처를 항상 구분해 표시한다.
- 확인되지 않은 값은 추정하거나 0으로 채우지 않고 "자료 부족" 또는 "확인 불가"로 표시한다. 한 출처가 실패해도 다른 출처의 값을 대신 쓰지 않는다.
- 공식 문서에서 확인되지 않은 주소, 요청값, 응답 항목을 추측하지 않는다. 가격을 사전 지식으로 채우지 않는다.
- 조회 전용이다. 계좌, 잔고, 주문, 정정, 취소 API는 연결하지 않는다.
- 공시 총액은 원 단위 정수(BigInt)로 보존한다. EPS·BPS·비율처럼 소수가 있는 값은 정밀도를 보존한다. 나눗셈은 분자·분모 또는 고정소수점으로 처리해 중간 정수 절삭을 피하고 표시할 때만 반올림한다. JSON에서는 BigInt를 문자열로 전달한다.

[표시 원칙]
- 금액은 "11조 3,145억 원"처럼 조·억 단위로 표시한다(억 미만 반올림). 비율은 소수 둘째 자리까지.
- 질문 01~04의 상태 문구는 "안정적으로 확인됨", "추가 확인 필요", "자료 부족"만 쓴다. 가격 질문(05)만 값이 확인되면 "수치 확인", 없으면 "자료 부족"을 쓴다. 가격에는 "안정적"이라는 말을 붙이지 않는다.
- "자료 부족"은 필요한 숫자가 없어 판단할 수 없을 때, "추가 확인 필요"는 숫자는 있는데 변동이나 주의점이 있을 때 쓴다. 둘을 섞지 않는다. 필요한 숫자가 하나라도 없으면 "안정적으로 확인됨"을 쓰지 않는다.
- 해석 문장에 회사명을 넣지 않고 "이 회사"라고 쓴다.

[작업 방식]
- 파싱·계산·오류 처리·비밀값 비노출에 필요한 테스트를 tests 폴더에 작성하고 node --test로 실행한다. 자동 테스트에는 가상 응답을 사용하고, 실제 API 검증은 별도로 수행한다. 실행하지 못한 검증은 미확인으로 보고한다.
- 작업이 끝나면 무엇을 만들었는지, 어떻게 실행하는지, 무엇을 확인하지 못했는지를 짧게 알려준다.
- 기존 AGENTS.md가 있으면 덮어쓰지 말고 충돌 여부를 확인해 병합한다.
- 이 작업은 고객 PC에서 실행할 로컬 프로그램 제작이다. 외부 공개, 터널링, 클라우드 배포를 자동으로 하지 않는다. 4318 포트가 사용 중이면 다른 프로세스를 종료하지 말고 원인을 알린다.
- 브라우저로 제공할 파일은 명시적으로 허용하고, API의 Host·Origin을 검증한다. 외부 사이트의 호출을 허용하는 CORS 설정을 넣지 않는다.
- .env.local의 내용을 화면이나 도구 출력으로 읽어 보여주지 않는다. 서버에서 읽고 설정 상태만 확인한다. 캐시에는 인증정보와 인증정보가 포함된 URL을 저장하지 않는다.
```

## 프롬프트 1 — 예시 데이터로 첫 화면

```text
국내 상장종목을 검색해 기업의 기본 정보와 재무 상태를 확인하는 반응형 웹사이트의 첫 화면을 만들어줘. 아직 실제 API는 연결하지 말고 예시 데이터로 구성하고, 화면에 "샘플 데이터"라고 표시해줘.

[파일]
- server.mjs, public/index.html, public/styles.css, public/app.js
- node server.mjs로 실행하면 http://127.0.0.1:4318 에서 열린다.

[화면 구성 — 위에서 아래로]
1. 머리말: 서비스명 "바치올 주가 실험실", 제목 "워런 버핏이라면 기업을 볼 때 어떤 숫자를 먼저 확인할까?", 설명 "공개적으로 알려진 그의 투자 관점을 다섯 가지 질문으로 정리했습니다. 시세와 공시에서 사실을 확인하고, 판단은 보는 사람에게 남깁니다."
2. 검색 영역: 회사명·종목코드·자연어를 입력하는 검색창, 후보 목록, "선택 종목 조회" 버튼.
3. 현재가 카드: 종목명, 종목코드, 현재가(원), 전일 대비와 등락률, 시가·고가·저가, 거래량, 시가총액, 52주 최저~최고, 외국인 보유비중, 시장구분·지수, 출처, 조회 완료 시각.
4. "다섯 질문 확인 결과" 요약: 질문 하나가 한 줄(질문 이름 · 상태 · 한 문장 설명). 종합 점수나 결론은 없다.
5. 다섯 장의 질문 카드. 번호(01~05)와 제목은 다음과 같다.
   01 꾸준히 돈을 버는가? / 02 자본을 효율적으로 쓰는가? / 03 부채를 감당할 수 있는가? / 04 현금이 실제로 남는가? / 05 현재 가격이 부담스럽지 않은가?
   각 카드에는 핵심 숫자 묶음, 출처·기준 기간 한 줄, "버핏이라면 여기서 무엇을 봤을까"라는 해석 칸(버핏의 관점 한 줄 + 이 회사의 숫자 한 문단)과 상태 표시, 접을 수 있는 칸 세 개(최근 5년 재무 추이 / 원본·공시 근거 / 계산 방법과 해석의 한계)가 들어간다.
   숫자마다 "공시 확인", "계산 확인", "KB 제공" 중 하나의 작은 표시를 붙인다.
6. 화면 맨 아래 고정 띠: 굵게 "좋은 기업인가? 그리고 지금 가격도 좋은가?", 옆에 작게 "정보 제공 목적이며 특정 종목의 매수 또는 매도를 권유하지 않습니다. 모든 투자 판단과 책임은 투자자 본인에게 있습니다. 워런 버핏·버크셔 해서웨이의 공식 도구가 아닙니다."

[레이아웃]
```

## 프롬프트 2 — KB증권 Open API 연결

```text
예시 시세를 제거하고 KB증권 Open API로 국내주식 시세를 서버에서 연결해줘. 인증정보는 .env.local의 KB_APP_KEY, KB_APP_SECRET을 서버에서만 읽어줘.

[공식 문서부터 확인]
- https://openapi.kbsec.com/apidoc_b2c 의 최신 공식 문서에서 인증과 국내주식 현재가·기업개요 조회 규격을 확인한다.
- 호스트, 포트, 경로, HTTP 메서드, 헤더, 요청 본문, 성공·오류 코드, 응답 필드, 단위, 호출 제한을 확인한 뒤 구현한다. 확인한 문서와 확인일, 사용하는 항목을 API_MAPPING.md에 기록한다. 인증정보나 인증정보가 들어 있는 요청 URL은 기록하지 않는다.
- 공식 문서를 읽을 수 없으면 사용자에게 해당 API의 문서 또는 공식 JSON·Excel 자료를 요청한다. 주소·필드·성공 코드를 추측하거나 이전 구현의 값을 검증 없이 사용하지 않는다.
- IP·MAC 등 추가 정보가 필요한지는 공식 규격에서 확인한다. 네트워크 구성을 임의로 변경하지 않고 값은 출력하지 않는다.

[연결과 값 처리]
- 인증 토큰은 서버 메모리에만 보관한다. 만료·재발급은 공식 규격에 맞추고 무한 재시도하지 않는다.
- 확정된 6자리 종목코드만 KB에 전달한다. 종목명이나 자연어는 전달하지 않는다.
- 현재가, 전일종가, 등락률, 시가·고가·저가, 거래량, 시가총액, 시장구분·지수, 52주 범위와 기업개요 지표는 공식 응답에서 확인되는 항목만 표시한다.
- 공백·선행 0·부호·소수점은 공식 형식에 맞게 파싱한다. 빈 문자열·누락·잘못된 형식은 0으로 바꾸지 않는다. 현재가는 양의 값인지 확인한다.
- 시가총액 단위는 공식 문서로 확인하고 원 단위로 변환한다. 현재가×상장주식수 비교는 보조 검증으로만 사용하며, 불일치 시 시점·주식수 범위를 확인한다. 비슷한 숫자가 나온다는 이유만으로 단위를 확정하지 않는다.
- 전일 대비는 현재가−전일종가로 계산한다. 등락률을 대조할 때는 공식 반올림 정밀도를 반영한다. 전일종가가 0 이하이면 계산하지 않는다.
- 화면의 조회 완료 시각과 API가 제공한 데이터 기준 시각을 구분한다. 체결 시각·거래 상태가 제공되지 않으면 추정하지 않는다. 캐시 결과에는 최초 조회 시각과 캐시 사용 여부를 표시한다.
- PER·PBR·EPS·BPS·배당수익률에는 KB증권 제공값이며 산식·기준일은 제공기관 기준임을 표시한다. 직접 계산한 값과 섞지 않는다.

[서버와 화면]
- GET /api/quote?symbol=6자리 를 만든다. 화면에 필요한 값과 출처·시각만 반환하고, 원본 응답 전체나 인증정보·IP·MAC은 반환하지 않는다.
- 형식이 잘못된 코드는 400, 공식적으로 종목 없음이 확인되면 404, 외부 API 장애는 502 등으로 구분한다. 연결 장애를 종목 없음으로 표시하지 않는다.
- 타임아웃, 호출 제한, 중복 요청 합치기와 짧은 캐시를 구현한다. 기업개요가 실패해도 정상적으로 받은 현재가를 유지한다.
- OpenDART 목록이 없어도 유효한 종목코드로 KB 시세를 조회할 수 있어야 한다.
- 인증 및 필요한 시세·기업정보 조회 경로만 허용한다. 계좌·잔고·주문·정정·취소 API는 연결하지 않는다.
- 지금은 종목코드로 조회한다. 회사명 검색은 다음 단계에서 추가한다. 출처는 KB증권 Open API로 표시한다.

끝나면 실제 조회 한 건의 화면 값과 같은 요청의 API 응답 값을 비교해줘. 인증정보는 출력하지 말고 비교 항목·일치 여부·확인 시각만 알려줘. 키나 권한이 없어 실행하지 못했다면 연결 완료라고 하지 말고 미확인 항목을 알려줘.
```

## 프롬프트 3 — 종목 검색과 공시 재무 연결

```text
금융감독원 OpenDART를 서버에서 연결해 종목 검색과 최근 5개 사업연도 재무를 가져와줘. 키는 .env.local의 OPENDART_API_KEY를 서버만 읽고, 요청 주소나 키를 출력하지 마. 기준은 https://opendart.fss.or.kr 의 공식 개발가이드야. 아래 계정 ID와 필드도 공식 문서 및 실제 응답으로 확인하고, 확인되지 않은 매핑은 적용하지 마.

[종목 검색]
- https://opendart.fss.or.kr/api/corpCode.xml (ZIP 안의 CORPCODE.xml)에서 stock_code가 6자리인 기업만 골라 회사명·종목코드·기업코드 목록을 만든다. 서버 캐시 폴더에 저장하고 24시간 지나면 다시 받는다.
- GET /api/companies?q=검색어: 회사명 일부, 6자리 종목코드, 또는 "현재 ○○ 주가가 얼마야?" 같은 문장을 받아 후보를 돌려준다. 문장 안에 회사명 전체가 들어 있으면 그 회사를, 독립된 6자리 숫자가 있으면 그 종목을 찾는다. 더 긴 회사명 안에 포함된 짧은 이름은 중복 후보로 만들지 않는다.
- 화면: 입력하면 후보 목록이 뜨고, 사용자가 후보를 고른 뒤 "선택 종목 조회"를 눌러야 시세와 재무를 조회한다. 입력 중에는 검색만 한다.
- 이름 → 종목코드는 우리 검색 기능이 하고, 종목코드 → 시세는 KB증권 Open API가 한다. 화면의 종목명은 KB가 돌려준 이름을 쓰고, 공시상 회사명이 다르면 함께 보여준다.
- 이 버전의 공시 재무 연결은 종목 목록에 매핑되는 기업 중심이다. 우선주·ETF·ETN 등 매핑되지 않는 대상에는 이 도구의 지원 범위를 안내한다. 이를 해당 상품에 공시나 재무정보가 전혀 없다는 뜻으로 설명하지 않는다.

[재무 조회]
- company.json으로 결산월(acc_mt)과 업종코드(induty_code)를 확인한다. 업종코드가 64, 65, 66으로 시작하면 금융업이다.
- fnlttSinglAcntAll.json을 reprt_code 11011(사업보고서)로 조회한다. 연결(fs_div CFS)을 먼저, 자료 없음(status 013)일 때만 별도(OFS)를 쓴다. 가장 최근에 공시된 완료 사업연도부터 연속 5개 연도를 가져온다. 아직 공시되지 않은 해를 추정하지 않는다.
- 금액은 thstrm_amount(당기) 문자열을 원 단위 정수로 읽는다. 같은 계정의 후보 금액이 서로 다르면 그 계정은 "자료 부족"으로 둔다.
- 계정은 표준 ID를 먼저 찾고, 없으면 계정명으로 찾는다(공백은 무시).
  · 매출액 ifrs-full_Revenue / 영업이익 dart_OperatingIncomeLoss / 지배주주순이익 ifrs-full_ProfitLossAttributableToOwnersOfParent (손익계산서 IS 또는 CIS)
  · 지배주주지분 ifrs-full_EquityAttributableToOwnersOfParent: 당기말은 thstrm_amount, 기초는 같은 보고서의 전기말 금액(frmtrm_amount)을 후보로 사용하되, 해당 사업연도 기초와의 일치 및 재작성 여부를 원문에서 확인한다. 불일치하면 임의로 기초값으로 쓰지 않는다
  · 부채총계 ifrs-full_Liabilities / 자본총계 ifrs-full_Equity / 현금및현금성자산 ifrs-full_CashAndCashEquivalents (재무상태표 BS)
  · 차입금: 단기차입금 ifrs-full_ShorttermBorrowings, 유동성장기차입금 ifrs-full_CurrentPortionOfLongtermBorrowings, 장기차입금 ifrs-full_LongtermBorrowings, 사채, 유동성사채, 유동 리스부채 ifrs-full_CurrentLeaseLiabilities, 비유동 리스부채 ifrs-full_NoncurrentLeaseLiabilities.
    - 같은 금액을 두 번 더하지 않는다. "유동성장기부채", "차입금 및 사채"처럼 여러 항목을 묶은 합계 계정(예: ifrs-full_CurrentBorrowingsAndCurrentPortionOfNoncurrentBorrowings)이 있으면 그 합계와 그 안에 포함된 세부 항목(유동성사채, 리스부채 등)을 함께 더하지 않는다.
    - 포함 관계는 사업보고서 원문의 차입금 주석 표에서 확인한다. 합계 계정의 금액이 주석의 세부 항목 합과 일치하면 세부 항목을 제외한다.
    - 이름에 "차입금", "사채", "리스부채"가 들어가는데 위 분류에 해당하지 않는 계정이 있으면 총차입금을 계산하지 않고 "자료 부족"으로 둔다. 금액이 음수이거나 원화가 아니어도 계산하지 않는다.
    - 주석과 대조하지 못했지만 재무상태표에 서로 겹치지 않는 항목으로 올라와 있으면 그대로 합산하고 화면에 "주석 미대조"라고 표시한다.
  · 이자비용 ifrs-full_InterestExpense. 손익계산서에 없으면 사업보고서 원문(document.xml ZIP)에서 찾는다. 금융원가 전체로 대신하지 않는다. 찾지 못하면 "자료 부족".
    - 원문에서 당기 연간 합계, 연결/별도, 통화·단위, 이자비용 계정과 표의 포함 관계가 모두 확인될 때만 사용한다. 특정 XML 속성 문자열이나 주변 글자 수만으로 기간·단위를 확정하지 않는다.
    - 괄호·음수는 원문 부호를 보존하고 비용 표시 관행이 확인될 때만 계산용 양수로 정규화한다. 동일 조건의 금액이 충돌하거나 단위·범위가 불분명하면 자료 부족으로 둔다.
  · 영업활동현금흐름 ifrs-full_CashFlowsFromUsedInOperatingActivities (계정명 "영업활동현금흐름", "영업활동순현금흐름", "영업활동순현금흐름 합계" 등도 인정. "영업활동에서 창출된 현금"은 다른 계정이므로 쓰지 않는다)
  · 유형자산의 취득 ifrs-full_PurchaseOfPropertyPlantAndEquipmentClassifiedAsInvestingActivities / 무형자산의 취득 ifrs-full_PurchaseOfIntangibleAssetsClassifiedAsInvestingActivities (현금흐름표 CF)
  · 기본주당이익 ifrs-full_BasicEarningsLossPerShare (없으면 "보통주 기본 및 희석주당이익" 같은 계정명)
- 회사마다 계정명과 ID가 조금씩 다르다. 찾지 못한 계정은 0으로 채우지 말고 그 항목만 "자료 부족"으로 둔다.
- OpenDART 응답은 서버 캐시 폴더에 저장해 같은 요청을 반복하지 않는다.

[서버와 화면]
- GET /api/financials?symbol=6자리 → 5개 연도의 원본 금액, 계정명, 계정 ID, 연결/별도 구분, 접수번호, 원문 링크(https://dart.fss.or.kr/dsaf001/main.do?rcpNo=접수번호).
- 조회 버튼은 KB 시세와 OpenDART 재무를 각각 요청하고 상태를 따로 표시한다. 종목을 바꾸면 이전 결과를 지우고, 늦게 도착한 이전 종목의 응답이 새 화면을 덮지 않게 한다.
- 각 질문 카드의 "원본·공시 근거" 칸에 연도별 원본 금액과 원문 링크를, "최근 5년 재무 추이" 칸에 5개 연도 표를 넣는다. 출처는 "OpenDART"로 표시해 KB 값과 구분한다.

끝나면 종목 하나를 이름으로 검색해 조회하고, 매출액과 영업이익이 공시 원문과 같은지 확인해줘.
- ZIP은 경로 이탈·압축 해제 크기 제한을 검사하고 XML 외부 엔티티를 처리하지 않는다. 인증 실패·호출 한도·통신 오류를 자료 없음으로 처리하지 않는다.
- 재무 캐시는 조회 시각과 만료 정책을 두고 재조회할 수 있게 한다. 정정공시는 접수번호와 기준을 다시 확인한다. 다년 비교에서 연결/별도, 기간 길이, 통화 및 재작성 기준이 맞지 않으면 비교하지 않는다.
- 취득 지출은 현금흐름표의 실제 지출인지 확인한다. 누락을 0으로 처리하거나 자산 처분액을 취득액에 섞지 않는다.
```

## 프롬프트 4 — 다섯 질문 계산과 화면

```text
가져온 숫자로 다섯 질문을 계산하고 카드와 요약을 채워줘. 아래 공식과 구분선은 이 도구가 정한 것이고 워런 버핏의 공식 기준이 아니야. 종합 점수나 매수·매도 판단은 만들지 마.

[계산 — 원 단위 정수로 계산하고 표시만 소수 둘째 자리]
- 영업이익률 = 영업이익 ÷ 매출액 × 100. 매출액이 0 이하면 계산하지 않는다.
- ROE = 지배주주순이익 ÷ ((기초 지배주주지분 + 기말 지배주주지분) ÷ 2) × 100. 연결 기준일 때만 계산하고, 지분이 0 이하면 계산하지 않는다.
- 부채비율 = 부채총계 ÷ 자본총계 × 100. 자본총계가 0 이하이면 계산하지 않고 사유를 표시한다.
- 이자보상배율 = 영업이익 ÷ 이자비용. 이자비용이 0이거나 없으면 계산하지 않는다.
- 총차입금 = 차입금·사채·리스부채 합계. 1년 내 상환액 = 그중 유동 항목 합계.
- 단순 잉여현금흐름 = 영업활동현금흐름 − (유형자산 취득 + 무형자산 취득). 취득 금액이 음수로 공시되면 지출액(양수)으로 바꿔 쓴다.
- 금융업(업종코드 64·65·66)에는 부채비율, 이자보상배율, 단순 잉여현금흐름 해석을 적용하지 않는다.
- 입력값이 하나라도 없으면 그 지표만 "자료 부족"으로 둔다.

[카드에 보여줄 핵심 숫자 — 최근 연도]
- 01: 매출액, 영업이익, 지배주주순이익, 영업이익률
- 02: 지배주주순이익, 평균 지배주주지분, ROE, 그리고 대조용으로 KB 제공 ROE
- 03: 총부채, 총차입금, 1년 내 상환액, 현금및현금성자산, 부채비율, 이자보상배율, 그리고 대조용으로 KB 제공 부채비율
- 04: 영업현금흐름, 유형·무형 취득 지출, 단순 잉여현금흐름
- 05: KB 제공 PER, PBR, EPS, BPS, 배당수익률, 그리고 대조용으로 공시 기본 EPS

[상태 — 질문마다 하나]
- 01: 5년 중 영업이익이나 순이익이 흑자가 아닌 해가 있거나, 영업이익률이 조회한 5개 연도 중 첫해보다 30% 넘게 낮아졌으면 "추가 확인 필요". 아니면 "안정적으로 확인됨".
- 02: ROE가 0 이하인 해가 있거나 조회한 5개 연도 중 첫해보다 30% 넘게 낮아졌으면 "추가 확인 필요". 아니면 "안정적으로 확인됨".
- 03: 현금이 총차입금 이상이면 "안정적으로 확인됨", 차입금이 더 많으면 "추가 확인 필요". 금융업은 "추가 확인 필요".
- 04: 최근 연도 잉여현금흐름이 플러스이고 5년 중 마이너스가 한 해 이하면 "안정적으로 확인됨". 아니면 "추가 확인 필요". 금융업은 "추가 확인 필요".
- 05: KB 제공 PER이나 PBR이 확인되면 "수치 확인"만 표시한다. 숫자가 있다는 뜻일 뿐이며 싸다/비싸다로 바꾸지 않는다.
- "자료 부족"이 먼저다. 그 질문의 판단에 필요한 숫자가 하나라도 없으면 다른 상태를 붙이지 않는다.
- 5년을 비교하는 질문(01, 02, 04)은 5개 연도가 연속되고 모두 같은 재무제표 기준(전부 연결이거나 전부 별도)일 때만 판단한다. 연결과 별도가 섞였거나 빠진 해가 있으면 "자료 부족".
- 과거 연도의 총차입금이 확인되지 않아도 03의 상태는 최근 연도의 현금과 총차입금으로 정한다. 다만 주석과 대조하지 못했다는 이유만으로 과거 연도 차입금을 비워 두지 말고, 재무상태표에 서로 겹치지 않는 항목으로 올라와 있으면 합산한다. 01은 5개 연도의 이익과 첫해·최근 연도의 영업이익률, 02는 5개 연도의 ROE, 03은 현금과 총차입금, 04는 5개 연도의 잉여현금흐름이 모두 있어야 한다.

[버핏의 관점 — 카드마다 한 줄]
- 각 카드의 해석 칸 제목은 "버핏이라면 여기서 무엇을 봤을까"로 하고, 제목 옆에 상태를 표시한다. 그 아래에 "버핏의 관점" 한 줄과 "이 회사의 숫자" 한 문단을 차례로 둔다.
- "버핏의 관점"에는 아래 취지를 해당 공식 주주서한에서 확인하고 한국어 요약으로 쓴다. 직접 인용인 것처럼 따옴표를 붙이지 않는다. 확인하지 못한 문장은 사용하지 않는다. 괄호 안의 출처는 카드 앞면에 표시하지 않고, 그 카드의 "계산 방법과 해석의 한계" 접힘 칸에 "버핏의 관점 출처: 버크셔 해서웨이 ○○○○년 주주서한" 링크로 넣는다. 출처와 일치하는지 확인한 뒤 사용하며, 이 회사에 대한 평가나 비교 문장을 덧붙이지 않는다. 어떤 종목을 조회해도 같은 문장이 나온다.
  · 01: 버크셔는 찾는 회사의 조건으로 “꾸준한 수익력이 입증된 회사”를 들었습니다. 미래 전망이나 실적 회복 기대에는 관심이 없다고 했습니다. (1987년 주주서한)
  · 02: 버크셔는 “부채를 거의 쓰지 않으면서 자기자본이익률이 좋은 회사”를 찾는다고 밝혔습니다. (1987년 주주서한)
  · 03: 버핏은 뛰어난 기업 대부분이 이자를 감당할 능력에 비해 빚을 아주 적게 쓰며, 정말 좋은 사업은 보통 빌릴 필요가 없다고 했습니다. (1987년 주주서한)
  · 04: 버핏은 회계상 이익에 감가상각비를 더한 뒤, 경쟁력과 판매량을 유지하는 데 필요한 설비 지출을 뺀 “소유주이익”을 봐야 한다고 했습니다. (1986년 주주서한)
  · 05: 버핏은 “훌륭한 기업을 적정한 가격에 사는 것이 그저 그런 기업을 훌륭한 가격에 사는 것보다 훨씬 낫다”고 했습니다. (1989년 주주서한)
  · 링크: https://www.berkshirehathaway.com/letters/1987.html , https://www.berkshirehathaway.com/letters/1986.html , https://www.berkshirehathaway.com/letters/1989.html
- 버핏의 관점과 이 회사의 숫자를 나란히 보여줄 뿐, "버핏이라면 샀을 것/안 샀을 것" 같은 결론은 쓰지 않는다. 비교는 보는 사람이 한다.

[이 회사의 숫자 — 한 문단 해석]
- 숫자를 다시 나열하지 말고, 5년 사이 무엇이 어떻게 변했는지를 2~4문장으로 쓴다. 미리 정한 규칙으로 문장을 조합하고 외부 AI를 호출하지 않는다.
- 예시: "ROE는 2021년 16.90%에서 2025년 7.70%로 크게 낮아졌습니다. 5년 평균은 10.48%, 가장 낮은 해는 2023년 5.50%입니다. 자본은 6조 2,456억 원에서 9조 1,655억 원으로 늘었는데 순이익은 1조 554억 원에서 7,061억 원으로 줄어, 자본이 늘어난 만큼 이익이 따라오지 못했습니다."
- 04 예시: "영업으로 1조 4,901억 원을 벌어 1조 2,463억 원을 설비·무형자산에 다시 넣었고, 2,438억 원이 남았습니다. 번 현금의 약 83%가 재투자로 나갔습니다. 최근 5년 중 2023년에는 투자가 번 현금보다 많았습니다."
- 05 예시: "KB증권 제공 기준으로 현재가 276,000원은 주당이익(EPS 6,563.57원)의 42.05배, 주당순자산(BPS 86,051.83원)의 3.21배입니다. 배당수익률은 1.39%입니다. 최근 52주 가격 범위는 83,200원~374,500원입니다. 이 숫자만으로 싸다, 비싸다를 판단하지 않습니다."
- 회사명, 질문형 문장, 종목을 사거나 팔라고 권하는 표현, 추천·저평가 같은 평가 표현을 넣지 않는다.
- 방향은 분명하게 쓴다. "낮아지거나 같았습니다"처럼 뭉뚱그리지 말고 "낮아졌습니다", "높아졌습니다", "같았습니다" 중 하나를 고른다. 30% 넘게 변했으면 "크게"를 붙인다.

["다섯 질문 확인 결과" 요약]
- 질문 하나가 한 줄: 번호와 질문 이름 · 상태 · 해석의 핵심 한 문장. 상태가 "추가 확인 필요"면 그 이유가 되는 문장을 보여준다.
- 아래에 "항목별 확인 상태이며 종합 점수나 매수·매도 판단이 아닙니다. 워런 버핏 또는 버크셔 해서웨이의 공식 기준이 아니라, 공개적으로 알려진 투자 관점을 바탕으로 구성한 질문입니다."를 넣는다.

["계산 방법과 해석의 한계" 칸]
- 질문마다 공식, 계산하지 않는 경우, 이 숫자만으로 판단할 수 없는 점을 적는다. 04에는 "단순 잉여현금흐름은 유지 투자와 성장 투자를 구분하지 않으며 버핏의 소유주이익과 다릅니다"를 넣는다.

계산과 상태 규칙에 대한 테스트를 추가해줘. 흑자가 아닌 해, 30% 넘는 하락, 자료 누락, 금융업, 분모 0인 경우를 포함해줘.
[상태와 해석의 예외 — 위 규칙과 함께 적용]
- 안정적으로 확인됨은 정해진 숫자 조건의 충족을 뜻하며, 기업·투자의 안전성이나 미래 실적을 보장하지 않는다고 상태 설명에 적는다. 특히 03은 현금과 차입금 비교만으로 상환능력을 확정할 수 없음을 밝힌다.
- 30% 하락은 첫해 값이 양수일 때 (첫해−최근)/첫해×100으로 계산한다. 퍼센트포인트 차이와 구분한다. 첫해가 0 이하인 경우 하락률을 계산하지 않고 흑자·ROE 조건에 따라 처리한다.
- 금융업 03·04는 일반기업 해석 비적용을 우선 안내한다. 필수 숫자가 누락되면 자료 부족, 숫자가 있어도 일반 기준으로 판단할 수 없으면 추가 확인 필요로 표시한다. 업종 자체가 확인되지 않으면 일반기업으로 가정하지 않는다.
- 주석 미대조로 총차입금 범위가 불확실하면 참고 합계를 표시할 수 있지만 03에 안정적으로 확인됨을 붙이지 않는다. 포함 관계가 불명확하면 총차입금은 자료 부족이다.
- 별도 재무제표에 지배주주순이익이 없으면 01에서 별도 당기순이익을 명확한 이름으로 표시할 수 있다. 5개 연도 전체가 같은 정의일 때만 비교하고, 02의 지배주주 기준 ROE로 대체하지 않는다.
- 위 숫자 예시는 문체 설명용이다. 실제 결과에 하드코딩하지 않는다. PER·PBR의 분모·기준일이 확인되지 않으면 현재가를 해당 EPS·BPS로 나눈 값과 같다고 단정하지 않는다.
- 소유주이익 설명에는 유지 투자 외에 필요한 운전자본 증가도 고려한다는 한계를 덧붙인다. 단순 잉여현금흐름과 같은 지표라고 표현하지 않는다.
```

## 프롬프트 5 — 실제 종목 검증과 오류 수정

```text
같은 업종이 아닌 국내 종목 두 개를 골라 종목명과 종목코드로 각각 실제 조회해서 검증해줘.

1. 종목명으로 조회한 결과와 종목코드로 조회한 결과가 같은 종목으로 연결되는지 확인해줘.
2. 화면의 현재가와 등락률이 KB증권 API 응답과 같은지, 매출액·영업이익이 OpenDART 응답과 같은지 비교해줘.
3. "자료 부족"으로 나온 항목마다 원본 응답에 값이 정말 없는 것인지, 계정 이름이나 ID가 달라서 못 찾은 것인지 먼저 확인해줘. 임의의 기본값으로 채우지 마.
   - 회사마다 계정명이 다를 수 있다. 예를 들어 주식 구분이 "보통주"가 아니라 "의결권이 있는주식(보통주)"로 오거나, 영업활동현금흐름이 "영업활동순현금흐름 합계"로 오는 경우가 있다.
4. 못 찾은 원인을 설명한 뒤 수정하고, 같은 두 종목과 잘못된 종목코드로 다시 테스트해줘. 잘못된 종목코드에는 다른 기업을 보여주지 말고 "종목을 찾을 수 없습니다"라고 안내해줘.
5. KB 제공 ROE·부채비율과 공시 계산값을 대조하되, 산식·연도·연결/별도 기준이 다르면 차이의 원인을 설명하고 억지로 일치시키지 마.
6. 같은 종목을 이름·코드·자연어로 검색했을 때 동일 후보인지 확인해줘. 원본 대조에는 동일 요청의 값을 사용해 조회 시차로 생긴 차이를 계산 오류로 오인하지 마.
7. 형식 오류와 공식적으로 존재하지 않는 종목, 인증 실패·통신 장애를 각각 검증해줘. 임의의 특정 코드를 영구적으로 존재하지 않는 코드라고 가정하지 마.

테스트 출력과 설명에 인증 정보나 접근 토큰, 원본 응답의 헤더를 포함하지 마.
```

## 프롬프트 6 — 모바일 화면·보안 최종 점검

```text
로컬 사용 전 최종 점검을 해줘. 고칠 것이 있으면 고치고, 항목별로 확인 결과를 알려줘.

[모바일]
- 390px 폭에서 가로 스크롤이나 잘린 항목이 없는지, 현재가 카드·요약·다섯 질문 카드가 한 열로 읽히는지 확인해줘.
- 조회 중, 자료 부족, 조회 실패 상태가 각각 화면에 제대로 안내되는지 확인해줘.
- 하단 고정 띠가 마지막 내용을 가리지 않는지 확인해줘.

[보안]
- 실제 키와 시크릿이 소스코드, Git 기록, 공개 파일에 없는지 확인해줘. 변수 이름만 있어야 한다.
- 브라우저가 받는 /api 응답에 키, 토큰, IP, MAC, KB 원본 응답 전체가 없는지 확인해줘.
- 일부러 오류를 내 보고(잘못된 종목코드, 인증 실패 가정) 오류 메시지와 서버 로그에 비밀값이 나오지 않는지 확인해줘.
- .env.local과 캐시 폴더가 웹 주소로 열리지 않는지(404) 확인해줘.
- 서버가 조회 API만 호출하고 계좌·잔고·주문·정정·취소 API를 호출하지 않는지 확인해줘.

[표현]
- 화면에 종합 점수, 목표주가, 저평가·고평가 판정, 특정 종목을 사거나 팔라고 권하는 문장이 없는지 확인해줘. 하단 고정 띠와 요약 아래 안내문의 "매수 또는 매도를 권유하지 않습니다", "매수·매도 판단이 아닙니다"는 권유가 아니라는 안내이므로 그대로 둔다.
- KB증권 제공값과 OpenDART 값의 출처가 모든 카드에서 구분되어 있는지 확인해줘.

확인은 키 값을 다시 보여주는 방식이 아니라 실제 시세 조회와 "설정됨/설정되지 않음" 상태로 해줘.
- 실제 인증값을 변경해 오류를 만들지 말고 가상 응답으로 인증 실패를 재현한다. Git 저장소가 없으면 기록 검사는 해당 없음으로 보고한다.
- 390px 검증은 PC 브라우저의 화면 폭 변경으로 진행한다. 127.0.0.1로만 실행하므로 별도 휴대폰에서 접속하도록 서버를 공개하지 않는다.
- 결과는 통과 / 수정 후 통과 / 미확인 / 해당 없음으로 구분하고, 실행한 검사와 남은 문제를 적는다. 정적 확인만 한 항목을 실제 동작 확인으로 보고하지 않는다.
- README에 실행·종료·재실행 방법과 필요한 설정 이름, 지원 범위, 데이터 한계를 정리한다. 실제 비밀값은 넣지 않는다.
```
